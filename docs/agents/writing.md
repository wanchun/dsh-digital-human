# 数字人写作规范

本文件规定五类文本的写法：人设、playbook、派单、回执、报告。
所有给人看的文档遵循 ASD-STE100 的 80%。

## 人设

人设是四段式。四段之外不写别的段落。

| 段 | 写什么 | 限制 |
|---|---|---|
| 身份 | 一句话：我是谁，为哪类需求服务 | 只写一句 |
| 输入 | 收到哪些字段，从哪来 | 只列字段，不写步骤 |
| 回执 | 回给谁，写哪几项 | 结论、证据路径、下一步 |
| 遇到这些情况 | 表格：情况 → 就做 | 一行一个条件，一个动作 |

- 正文不超过 600 字。字数不含 frontmatter 与标题。
- 身份段只写一句。职责清单放输入段或 playbook。
- 输入段只写字段与来源。不写“先读 A 再读 B”。
- 回执段只写结论、证据路径、下一步。不复述过程。
- 情况表一行一个触发条件。一个动作。动作以动词开头。
- 人设不写流程。流程属于 playbook。

### 依赖声明

人设可以点名技能。点名时写依赖说明：

```
依赖技能：<技能名>（用它做<哪一步>）
```

- 依赖行放在输入段末尾。
- 一步一行。
- 技能名必须等于 `~/.agents/skills/<技能名>/` 的目录名。
- 人设不点名技能，就不写依赖行。
- 依赖说明只给人看。插件不解析、不校验，也不因缺技能拒绝启动。

## Playbook

- 正文不超过 1500 字符。
- 结构固定：前置检查、步骤、完成判据、回执字段。
- 每一步写一个动作和一个完成判据。
- 不写背景、历史、原因。只写怎么做与何时算完成。
- 长命令、大表格、样例放进同目录的 `references/<主题>.md`。
- playbook 只留指针：`细节见 references/<主题>.md`。
- playbook 不复制别处的文档。要引用时写绝对路径。

## 上下文预算

每轮按下面的顺序取上下文。这是可执行规则，不是建议。

1. 先读需求摘要：`digital_human_requirement_read`。摘要不超过 4KB。
2. 只读当次任务需要的文件。路径从摘要或派单的 facts 取。
3. 不遍历目录，不读整个仓库，不重读历史会话。
4. 证据文件只读结论段：标题、结论、证据指针。
5. 需要细节时，按证据里的路径再读那一个文件。
6. 本轮结束前把结论写回 `state.json` 或回执。细节用 `digital_human_requirement_attach` 落盘。
7. 上下文超预算时，先写一句摘要：结论加指针。再继续。不把全文贴进上下文。

一句话：每轮只读需求摘要和当次所需文件；证据只读结论段。

## 派单

派单只传事实与上下文，不传做法。

| 字段 | 说明 |
|---|---|
| requirement | 线程名与需求目录绝对路径。工具写入消息头。必填。 |
| task_id | 工作项 id。 |
| node | 节点名。可空。空表示由执行者判断。 |
| facts | 子系统、版本、分支、环境、仓库、相关文档绝对路径。 |
| context | 当前进度一句话，加上一步结论的指针。不贴全文。 |
| message | 正文写要什么结果、验收判据、要什么证据。 |
| expect_receipt | 派活才带。提问、答复、回执、取消不带。 |

- 禁止字段：步骤列表、命令、注意事项。
- 工具拒绝携带这些字段的调用，并在错误里说明原因。
- 节点适用性由执行者判断。跳过节点时，在回执与 `state.json` 写理由。
- 负责人只校验结论与证据是否合理。不预先规定节点序列。

消息头用固定格式。工具负责写入，人不用手写：

```text
需求目录：<绝对路径>
工作项：<task_id>
节点：<node>
事实：
- 子系统：<子系统>
- 版本：<版本>
- 分支：<分支>
- 环境：<环境>
- 仓库：<仓库绝对路径>
- 文档：<文档绝对路径>
上下文：<一句话进度>；上一步结论见 <路径>

<可选的正文>
```

## 技能库

- 技能只有一处：全局 `~/.agents/skills/<技能名>/SKILL.md`。手工放进去，插件只读。
- 插件不再有第二份技能库，也没有上传入口。
- 数字人记录 `config.skills` 是唯一开关，列出勾选的技能名。未勾选的技能由影子屏蔽，对该数字人不可见。新建记录默认全勾。
- 配置页列出全局全部技能。勾选的正常显示，未勾选的灰显。
- 判定标准：一条规则若「不勾选就没法工作」，它属于机制，不属于技能。机制写进插件的操作上下文，不进库、不进勾选列表。`digital-human-comms` 按机制处理。
- 人设可以写 `依赖技能：<名字>（用它做<哪一步>）`。这是给人看的说明文字，插件不解析、不校验。

## ASD-STE100 的 80%

- 一句一个意思。长句拆开。
- 用主动语态。写清谁做什么。
- 一句不超过 25 个汉字。
- 用词固定。术语与 `GLOSSARY.md` 一致。
- 不写比喻，不省略主语，不用双重否定。
- 命令、路径、字段名保持原样。

## 九条判据（写之前先过一遍）

1. **机制已保证的不写。** 工具会报错的（字段被拒、必填缺失），写了只会让模型以为要自己判断。
2. **同一条规则只写一处。** 人设与技能、核心准则与职责细则之间不许重复；重复必漂。
3. **判据跟着动作走，模板进技能。** 人设写「做到什么算完」，技能写「长什么样」。
4. **只写本角色的判断。** 执行者报事实，不判超时、不判该不该跳过——判断归调度者。
5. **派单只传事实。** 步骤、命令、注意事项不传；传了会挤掉真正的事实。
6. **写做什么，少写别做什么。** 禁止清单只列真会犯的，不列想象出来的。
7. **一个文件一个写者。** 两个写者必然互相覆盖，写前先看归属。
8. **每步带工具名。** 不点名时模型会自己找路：手写文件、绕开工具。
9. **写之前先问：这句话不写，模型会做错吗？** 不会就删。

## 一句总原则

> 人设只写机制没保证、且模型真会做错的事。其余都删。
