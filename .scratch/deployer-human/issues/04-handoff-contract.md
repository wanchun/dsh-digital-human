# 04 · 派单与回执契约

Type: grilling
Status: resolved

## Question

研发助手 → 部署人 的这条派单，消息里到底要带什么？回执要带什么？

**派单（研发助手发）**——候选字段：
- 版本目录（过程目录路径）
- 子系统（可多个）+ 目标环境（idc）
- 部署分支 / 版本号
- 是否首轮确认（部署人自己判，还是派单方声明）
- 期望：终态成功 / 失败时给什么证据

**回执（部署人回）**——候选：
- 结论（成功/失败/阻塞）+ 流水执行 id + 包名/版本 + 环境
- 失败时的归因提示（构建失败 / 分支不一致 / 环境被占 / 凭据）
- 指向落盘证据的路径

➡️ 推荐：派单只给**指针与事实**（版本目录、子系统、环境、分支），不贴日志；回执只给**结论 + 执行 id + 证据路径**，失败必带一条归因。

另外要定：部署人是否直接和自测助手说话（部署成功→派自测），还是必须经研发助手中转。
## Answer

**派单方 = PM。** 依据（用户口径）：PM 把控一个需求的进度，它需要知道下一步做什么；其它助手只做具体的事。

分工：

| 角色 | 职责 |
|---|---|
| PM | 调度：派部署、派自测、通知研发冒烟/修复、汇总、对外 |
| 研发助手 | 执行 A 开发 / B 合并 / C 验证 / F 冒烟 / 修复环 |
| 部署人 | 执行 D：查占用 → 校验分支 → 触发 → 轮询 → 回执 |
| 自测助手 | 执行 E：按派单验 |

**回执单点**：部署人只回 PM（派单方），不回研发助手；PM 再决定下一步派给谁。
**消息只带指针**：跨数字人的消息一律带 `task_id`，收到方先读 `digital_human_status` 再动作——账本是唯一事实来源。

**派单字段**（PM → 部署人）：子系统、目标环境（IDC）、版本、部署分支、版本目录路径、是否已确认。
**回执字段**（部署人 → PM）：结论（成功/失败/排队中/待确认）、triggerId、包名、环境、证据路径、失败归因（分支不一致 / 构建失败 / 环境被占 / 凭据）。
**首轮确认**：部署人回 `needs-confirm`，PM 用现有 bot 问人，确认后 PM 重派并带 `confirmed=true`（避免部署人再绑一个 bot）。
