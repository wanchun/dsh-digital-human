# Spec: 需求流程 v2（自测入链 + 总表双列 + PM 瘦身）

Status: ready-for-agent

## Problem Statement

现在的需求流水线能跑，但四个地方在漏：

1. **总表状态已经漂移**：声明的是 `待确认/待启动/进行中/已完成/阻塞/已终止/外部执行中`，真实行里却是「待审 PR !4」「已合并（待 DDL 与发布）」「已完成（F1 已发布，待测试验证）」——这些是阶段，不是状态，下游按状态判断会卡住。
2. **同一张表两个写者**：PM 写建档状态，研发写执行状态，靠纪律而不是结构隔离。
3. **后台发布后没有自测门禁**：研发部署成功就直接冒烟；需求与代码影响范围的自测靠人，漏了也没人知道。
4. **PM persona 39KB 与技能重复**，通知要三级回退 chatId，且自测助手游离在流程之外。

## Solution

- 总表拆成两列、两个写者：`建档状态`（PM）+ `执行状态`（研发），自由文本退回 `备注`，再加 `当前节点`。
- 节点链从 A–E 改为 A–F：**E 自测**（后台发布成功后、冒烟前），**F 冒烟**；自测由研发派给自测助手，通过才允许冒烟。
- 研发 ↔ 自测直连（peers 双向），自测证据落在版本目录的 `self-test/`（自测助手独占），研发只写节点摘要。
- PM persona 去掉与 `qs-end-to-end-fast` 重复的部分；通知改为一级查找（项目固定群 → 私发触发人），先补齐缺失 chatId。
- 技能加角色路由与 E/F 节点；自测失败进现有修复循环；自测“通过”= 影响范围内无新增失败。

## User Stories

1. 作为 PM，我想只维护 `建档状态/备注`，不再转抄执行状态，以便不和执行侧互相覆盖。
2. 作为研发助手，我想只写 `执行状态/当前节点`，以便实时反映自己在哪个节点。
3. 作为看板读者，我想每一行状态都能被枚举校验，以便脚本/人一眼判断下一步。
4. 作为研发助手，我想在部署成功后把自测任务派给自测助手，以便发布前有一道技术门禁。
5. 作为研发助手，我想在自测通过后才进入冒烟，以便不带疑点往下走。
6. 作为研发助手，我想在自测失败时进入现有修复循环，以便复用同一套 coder→pusher→deployer。
7. 作为自测助手，我想从 params/version/PR diff 推导影响范围，以便不被派单方限定死。
8. 作为自测助手，我想在允许范围内造测试数据并记录，以便不逐次等审批。
9. 作为自测助手，我想把证据写进版本目录的 `self-test/`，以便研发只引用路径。
10. 作为自测助手，我想把结论回给派单的研发会话，以便回执不落错地方。
11. 作为 PM，我想在研发的完成消息里看到自测结论，以便转测试群时一并说明。
12. 作为维护者，我想技能里写清 PM 读哪几节、研发读哪几节，以便两边不读串。
13. 作为维护者，我想把现有 5 行总表迁移成新列，以便从第一天就只有一套格式。
14. 作为维护者，我想在自测超时（30 分钟）时标阻塞并附证据，以便不无限等。
15. 作为维护者，我想极速路径可跳过自测/冒烟但必须记录理由，以便小改动不被拖慢。
16. 作为维护者，我想纯前端需求跳过自测，以便不在没有后台发布时硬造门禁。
17. 作为维护者，我想补齐 project-info 缺失的测试群 chatId，以便 PM 只做一级查找。
18. 作为维护者，我想让历史文档保留旧节点字母，以便不重写历史。
19. 作为维护者，我想自测助手保持 single 会话串行，以便多个需求不同时打环境。
20. 作为维护者，我想自测通过口径是“无新增失败”，以便存量问题不阻塞发布。

## Implementation Decisions

**总表结构。** 列改为：需求名称 / 项目 / 子系统 / 版本 / 过程目录 / `建档状态` / `执行状态` / `当前节点` / 触发人 / 最近更新 / `备注`。
- `建档状态`（PM 写）：`待确认` / `已建档` / `已终止`。
- `执行状态`（研发写）：`待启动` / `进行中` / `自测中` / `冒烟中` / `已完成` / `阻塞` / `未上线`。
- `当前节点`（研发写）：`A 开发` / `B 合并` / `C 验证` / `D 部署` / `E 自测` / `F 冒烟` / `完成`。
- `备注` 由 PM 写摘要；研发的细节留在 progress.md，不再往总表塞自由文本。

**节点链。** A 开发 → B 合并 → C 验证 → D 部署 → **E 自测** → F 冒烟。历史节点的旧字母（E=冒烟）不改，只在 `nodes/` 历史文件里保留。

**复杂度路由。** 极速：自测与冒烟都可跳过，但必须在 `version.md` / `progress.md` / `final-report.md` 三处记录理由；标准/完整：跑 E 自测，F 冒烟按原规则；纯前端需求没有后台发布，跳过 E 并记录。

**研发 → 自测派单契约。** 研发在 D 部署 SUCCESS 后，用 `digital_human_send` 发给 `qa-assistant`：
- `conversation_id`：`<版本slug>-self-test-w<N>`（ASCII，按工作项唯一）；
- message 只给指针与事实：版本目录、`params.md` 路径、PR/merge commit、部署包/版本、环境与主机、验收标准、允许操作范围、报告落盘路径；
- 不写自测范围（范围由自测助手推导），不附大段日志。

**自测回报契约。** 自测助手回给派单会话（消息头 `session`），内容：通过/不通过、影响范围、新增失败清单、存量/已知问题、证据路径；不直接找 PM。

**自测落盘。** 自测助手写 `docs/qs-end-end/<版本目录>/self-test/w<N>-<YYYYMMDDHHmm>.md`（自测助手独占）；研发写 `nodes/w<N>-<序号>-self-test.md` 摘要并引用该路径。

**通过口径。** 通过 = 影响范围内没有新增失败；存量/已知问题单列，不阻塞冒烟。范围由自测助手从 `params.md` + `version.md` + PR diff + 部署版本推导。

**允许操作范围。** 研发在派单里写明：允许测试环境接口调用、带唯一前缀的幂等测试数据；禁止 DDL、改配置、重启其它服务。自测助手逐条记录写操作；超出范围先回报研发，由研发决定是否升级给 PM/触发人。

**失败与超时。** 自测失败回到现有修复循环（同一 uuid，coder→pusher→deployer），重新部署后重跑；轮次与现有修复循环共用，≤3 轮后标 blocked 并附证据。研发每 1 分钟 `digital_human_status` 轮询，上限 30 分钟；超时标阻塞并附自测当前证据。

**会话与 peers。** 自测助手保持 `single`；研发 `peers` 增加 `qa-assistant`，自测 `peers` 增加 `dev-assistant`；PM 仍是唯一对外前台。

**技能改动。** `qs-end-to-end-fast` 顶部加角色路由：PM 读 §0–3 + `preflight-inputs/project/report`；研发读 §0、§2–10 + `node-*/fix-loop/polling/report`；两边的 references 不再互相读。节点表加 E 自测、F 冒烟，修复循环与报告模板同步；新增 `references/node-self-test.md`。

**persona 改动。**
- PM：删除与技能重复的参数清单/版本目录规则；总表只写 `建档状态/备注`；完成消息核对自测结论；通知改为一级查找（项目固定群 → 私发触发人）。目标 39KB → 约 20KB。
- 研发：节点链改为 A–F；D 成功后派 E 自测并轮询；`执行状态/当前节点` 由自己写；总表只改自己的列；失败进修复循环。
- 自测：新增“发布后自测”一节（收派单 → 推导范围 → 执行 → 落盘 → 回报研发）；写操作按允许范围；不接需求、不建档、不转派。

**通知数据。** 补齐 `project-info.md` 中缺失的测试群 chatId（当前两个项目为「待登记/未登记」）；PM 只做一级查找。命名目标（`<项目>-测试群`）不在本次范围。

**迁移。** 现有 5 行手工映射，原状态文本全部进 `备注`；迁移前备份 `project-list.md.bak-<日期>`。映射：

## Testing Decisions

这是流程与提示词改动，没有新增代码接缝。验证以“走查 + 一次试点”为主：

1. **总表校验**：迁移后每一行的 `建档状态/执行状态/当前节点` 都在枚举内；PM 只改前两列，研发只改后两列。
2. **技能/ persona 一致性**：技能节点表、研发 persona 节点链、报告模板三处的 E/F 字母与顺序一致；PM persona 不再重复技能里的参数清单。
3. **派单/回报走查**：用一个低风险后台需求做试点，跑 A→F；检查研发派单消息是否只有指针、自测是否落 `self-test/`、回执是否回到研发会话、通过后是否才冒烟。
4. **失败/超时路径**：人为让自测报一次不通过，确认进修复循环；或让自测超过 30 分钟，确认标阻塞。
5. **PM 瘦身回归**：试点期间 PM 仍能完成权限门禁、参数确认、建档、转测试群，没有因为删重复段落漏步骤。

## Out of Scope

- ds-bot 式上下文管理（checkpoint/steward/FTS）——另议。
- 通知目标命名（`<项目>-测试群`）与 IM 侧改造。
- 自测助手改 `thread` 模式。
- 数字人插件代码改动（本次只改技能、persona、配置、文档）。
- 重写历史节点文件或历史进度。

## Further Notes

- 这是流程配置，不是插件代码；回滚 = 恢复技能/persona/总表备份。
- 历史文档保留旧字母（E=冒烟），新文档一律 A–F。
- 试点建议选一个单仓库、标准复杂度的后台需求，避免跨仓库同时引入太多变量。
