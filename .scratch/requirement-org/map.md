# Map: 需求级数字人组织

## Destination

一套**按需求装配**的数字人组织：PM 只对外，研发负责人一个需求一个会话，开发/自测/部署是被它调度的执行者。
终点是一份能直接转实现的规格，覆盖四块：**插件怎么改、五条人设怎么写、技能文档怎么改、现有文档怎么重组**。

取代 [deployer-human](../deployer-human/map.md)（那份是"只加一个部署人"的旧思路，PM 派单的判断已被推翻）。

## Notes

- **规则边界**：流程只到「上线检测」，OK 即结束。生产同步与运维部署不在规则内。
- **一个 bot 只服务一条记录**（实测）；需要对外说话的记录才绑 bot。
- **记录 vs 会话**：记录是配置；会话按需求派生。但 **PM 是多会话的**——dsh-im 按聊天建会话（私聊/群/不同人各一个），由 PM 人设判断说话人身份。
- **机制改动必须 opt-in**：`sessionWorkspace` / `memoryScope` 两个记录级开关；PM 都是 `record`，不改变 dsh-im 现有行为。
- **名称归人设**：线程名怎么起由人设决定，插件只要求唯一、稳定。
- 验证一律在沙箱（`~/.dsh-sandbox`，3099），不碰生产；生产改动要人确认后重启。
- 五个角色：PM / 研发负责人 / 开发助手 / 自测助手 / 部署助手。

- [03 · 记忆按会话隔离](issues/03-session-memory.md): 全员按会话分片，`memory/<线程名>.md` + `_shared.md`；各自压缩归档；旧记忆降级为 shared。
- [04 · 账本与需求的对应](issues/04-ledger-scope.md): 全员一需求一会话后，`conversation` 即需求，账本无需加字段。
- [01 · 职责矩阵与调度链](issues/01-roles.md): 负责人与开发"一需求一会话"；自测/部署各一条记录、一个会话服务 N 需求；因此 single 模式下账本必须自带 requirement。

## Not yet specified

- [09 归档与召回](issues/09-archive-recall.md)：上线后归档、PM 索引、恢复靠新会话。
- [10 需求目录与 worktree](issues/10-requirement-dir.md)：每需求一个目录，代码用 worktree，归档删除。

- 上线检测要不要一个角色来做（第一批不做）。
- 需求收尾后，负责人的会话要不要归档、怎么归档（会话多了以后）。
- 多个负责人之间要不要互相看得见（跨需求依赖）。

## Out of scope

- 生产部署、生产包同步、运维交接。
- 改 pace / qs 平台本身。
- 多租户或权限隔离（现在都是 danger-full-access）。
