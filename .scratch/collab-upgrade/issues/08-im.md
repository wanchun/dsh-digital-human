# 08 · IM：入站与升级到人

Type: grilling
Status: resolved

## Question

IM 只有出站，要不要补入站派发与「升级到人」？

## 现状（README 已知限制）

1. 同伴触发的 turn 会不会自动推到 IM 群，未验证 —— 目前靠主动 `notify_bot`。
2. IM 插件只能对「已经跟它说过话的会话」主动发 —— 新群/新联系人要先有入站消息。
3. 未绑定 IM bot 的数字人没有 `notify_bot`。

Halo 有：owner-claim（谁是主人）、identity-resolve（IM 身份↔数字人）、connection-arbiter（多端仲裁）、escalation-cut（升级到人的截断）。

## 可选

- **A 补出站**：同伴 turn 结束按规则推 IM（补限制 1）。
- **B 升级到人**：超时/失败自动 `notify_bot` 给负责人（与 04 的 deadline 联动）。
- **C 入站路由**：群消息落到该群对应的数字人会话（依赖 IM 插件开接口）。

➡️ 推荐 B 优先，A 次之，C 等接口。
## 侦察补充

- 升级到人是独立工具 `report_to_user`，配置 `escalation{enabled, timeout_hours=24}`。
- **切点有硬约束**：所有 `tool_use` 都拿到 `tool_result` 才允许切（`escalation-cut.ts:49-65`），否则 transcript 续不回来。
- 团队内升级会置 `waiting_user` 并把 `awaitingDecision` 广播给全办公室（`orchestration.ts:1220-1242`）；IM 侧问题私聊推 owner，群里只发"在等主人决定"（`im-escalation.ts:20-102`）。

➡️ **修订**：B 照这个形状做——给 `notify_bot` 加 `escalation` 语义与默认 24h 超时；切点规则先不碰（DSH 回合结束才回调，天然满足）。
## Decisions

- Q1 推送时机：**C**。只在工作项 failed / blocked / 超时时推；done 不推（回执走 04，给派单方）。
- Q2 推给谁：**A**。私聊 owner。群只在显式要求时，且只发一行「在等主人决定」（Halo 的做法）。
- Q3 超时：**C**。deadline 可显式给；不给就用记录里的默认值（建议 30 分钟）。超时必须有兜底值。
- Q4 入站：**A/C**。维持 bot↔数字人一对一，不做群路由表，等 05 定了形态再说。
- 去重：一条工作项最多升级一次（按 task id）；同一会话 5 分钟内的多次升级合并成一条。
- 未绑 bot 的数字人：不提供替代通道，不做 outbox 文件。

## Answer

**只回答一条路：没有 IM 来源的那条。**

有人从 IM 发消息进来 → IM 插件负责把回复送回原会话，与本单无关。
数字人之间派活 → 目前结果只落在派单方的会话里，外部不可见。这是要补的。

**规则**

1. 工作项进入 failed / blocked / 超时 → 给该数字人绑定的 owner 发一条私聊。
2. 内容只有三样：哪个工作项、什么状态、为什么（`reason` 一行）。不附日志。
3. 一条工作项只发一次；同会话 5 分钟内合并。
4. done 不发。

**依赖**：04 的任务终态与 deadline 字段；owner 认领已实现（`src/lib/im.ts:194`）。

**不做**：入站路由表、群内实时直播、未绑 bot 的降级出口。
